Hell's Kitchen Delivery: sistema em execução

Evidências do funcionamento do Trabalho 2 (Frontend → API Gateway → microsserviços gRPC → PostgreSQL), colhidas com o sistema rodando em Docker neste computador, em 27/11/2026.

1. Como o sistema foi colocado no ar

Um único comando sobe todas as peças (cada uma é um container com imagem própria, construída por um Dockerfile multi-stage):

docker compose up -d --build
# COMPOSE_PROFILES=banco-local,servicos,gateway,frontend,rastreamento

2. Arquitetura

O navegador fala só com o Gateway. O Gateway autentica o token, confere o papel, valida o JSON e traduz para Protobuf. Os três microsserviços gRPC têm o seu próprio contrato .proto; o Pedidos consulta o Catálogo (ConsultarItens) para validar e precificar. Todos os dados ficam no PostgreSQL. No Google Cloud as mesmas imagens rodam no Cloud Run, com o Cloud SQL (ver nuvem/Evidencias-na-nuvem.pdf); aqui, no computador, rodam no Docker Compose.

6. Chrome DevTools: o frontend só fala com o Gateway

Painel Network do Chrome DevTools durante o login e a navegação do cliente. Todas as chamadas de dados vão para 127.0.0.1:8000 (Gateway); nenhuma chega aos microsserviços. O cabeçalho X-Requisicao-Id liga a chamada aos logs dos serviços.

7. Rastreamento distribuído (Jaeger)

Cada requisição gera spans no Gateway, no Pedidos, no Catálogo e no banco, ligados pelo mesmo trace.
