1Contextualização e motivação

O Hell's Kitchen Delivery é o sistema de pedidos de um restaurante, com dois papéis que enxergam o mesmo dado por lados diferentes. O cliente cria a conta, monta a sacola a partir do cardápio (escolhendo, por exemplo, o sabor do refrigerante ou a água com ou sem gás), informa a entrega e acompanha o pedido em tempo real. A cozinha mantém o cardápio (pratos, descrições, fotos, preços e disponibilidade do dia, inclusive de cada opção), aceita os pedidos novos, avança as etapas até a entrega e vê em destaque os atrasados. Toda escolha oferecida ao cliente tem um controle correspondente na cozinha.

O domínio se divide em três contextos com dados e ritmos de uso próprios: Usuários (contas, credenciais e dados de entrega), Catálogo (o cardápio, lido por todos os clientes a cada 30 s e alterado pela cozinha) e Pedidos (escrita transacional, histórico de etapas e eventos em tempo real). Cada contexto é um microsserviço gRPC dono das próprias tabelas, sem chave estrangeira entre serviços; o pedido guarda uma cópia dos itens comprados. À frente deles, um API Gateway é a única porta de entrada do navegador: valida o JWT e o corpo da requisição, traduz JSON para Protobuf e concentra a política de tolerância a falhas.

No Trabalho 2 esse sistema rodava em três VMs do Compute Engine, e o grupo administrava sistema operacional, Docker, firewall, IPs fixos e a lista de IPs autorizados no banco, pagando pelas máquinas 24 horas por dia mesmo sem uso. A motivação desta etapa é entregar essas responsabilidades à plataforma. Cada componente virou uma imagem de contêiner publicada no Artifact Registry e implantada no Cloud Run, que fornece HTTPS com certificado automático, escala de zero a duas instâncias por serviço, substituição de instâncias com falha e logs centralizados. O PostgreSQL continua no Cloud SQL, agora acessado pelo conector do Cloud Run com autorização via IAM, e as senhas saíram dos arquivos .env para o Secret Manager. O resultado é uma infraestrutura 100% gerenciada, sem VM ligada, que fora do horário de uso custa centavos: o Cloud SQL é desligado entre os testes por um script.

2Arquitetura no Google Cloud

A Figura 1 mostra os componentes implantados no projeto sistemas-distribuidos-505422, região us-central1, e a Tabela 1 resume o papel de cada serviço gerenciado. O caminho de um pedido (POST /pedidos) atravessa todas as camadas:

  1. O navegador baixa a interface do delivery-frontend; o arquivo /config.js, gerado pelo nginx a partir da variável API_URL, informa o endereço do Gateway.
  2. A chamada de dados vai direto ao delivery-gateway com Authorization: Bearer. O Gateway barra na borda o que é inválido (401 sem token válido, 403 sem o papel exigido, 400 para corpo fora do contrato) antes de qualquer chamada gRPC, e tira o dono do pedido do próprio token.
  3. O Gateway monta o CriarPedidoRequest (Protobuf) e chama o delivery-pedidos por gRPC sobre HTTP/2 com TLS (porta 443), anexando um ID token da sua conta de serviço. O Cloud Run só entrega a chamada se essa conta tiver roles/run.invoker no serviço.
  4. O Pedidos confere preço, disponibilidade e opção de cada item no Catálogo (ConsultarItens) com o prazo que resta da chamada original e grava pedido, itens e primeira etapa numa única transação no Cloud SQL; um pg_notify na mesma transação alimenta o tempo real.
  5. A resposta volta como JSON (201). O id da requisição (X-Requisicao-Id) é o trace id e aparece em todas as linhas de log do caminho.

Endpoints públicos e privados. Os cinco serviços têm endpoint HTTPS público gerenciado pelo Cloud Run (domínio run.app, certificado automático). Frontend e Gateway aceitam qualquer cliente; os três microsserviços exigem o ID token de uma conta de serviço autorizada e respondem 403 a quem não o apresenta. Assim continua valendo a regra do Trabalho 2: o navegador só fala com o Gateway, e ninguém chega ao gRPC sem passar pela validação do JWT.

Dockerfiles e imagens

Há um Dockerfile por papel: frontend/Dockerfile, docker/gateway.Dockerfile, docker/migrador.Dockerfile e docker/microsservico.Dockerfile, que gera Usuários, Catálogo e Pedidos pelo argumento SERVICO. Todos são multi-stage. No Gateway e nos microsserviços, um estágio compila os .proto (o grpcio-tools fica fora da imagem final), outro instala as dependências num venv com cache do BuildKit e remove o pip, e o final copia só o venv, os stubs e o código do componente, já compilado em bytecode; o migrador segue o mesmo padrão sem o estágio dos stubs, e no frontend o Node existe só no estágio de build: a imagem final é o nginx com os arquivos estáticos. Todas rodam sem root; os serviços têm HEALTHCHECK e recebem o SIGTERM no processo principal, para encerrar de forma limpa; e o .dockerignore funciona como lista de permissão. As dependências são separadas por papel: o Gateway não leva o driver do PostgreSQL e o migrador não leva gRPC.

4Estratégia de resiliência

Na nuvem, falha parcial é rotina: instância que sobe a frio, revisão nova substituindo a anterior, banco reiniciando, oscilação de rede. A estratégia combina recursos da plataforma com mecanismos no código, concentrados na classe ClienteResiliente (src/comum/resiliencia.py), usada pelo Gateway para chamar os três microsserviços e pelo Pedidos para chamar o Catálogo, e no interceptador comum dos servidores gRPC (src/comum/servidor_grpc.py). Todos os parâmetros vêm de variáveis de ambiente com valor padrão.

Tabela 4. Mecanismos de tolerância a falhas.
MecanismoFuncionamentoConfiguração no Cloud Run
Timeout e prazo totalCada tentativa tem um limite e a soma das tentativas também: nenhuma requisição fica pendurada esperando um serviço lento.GRPC_TIMEOUT=10 s e GRPC_PRAZO_TOTAL=25 s (5 e 12 s no ambiente local; a folga cobre a partida a frio)
Retry com backoffAté 3 tentativas, com esperas de ~0,2 s e ~0,4 s sorteadas entre 50% e 100% (jitter) para os clientes não repetirem juntos. Só repete o que é seguro: UNAVAILABLE sempre, pois ocorre antes de qualquer escrita; DEADLINE_EXCEEDED e CANCELLED só em operação idempotente.RETRY_TENTATIVAS=3
IdempotênciaO Gateway gera o pedido_id antes da primeira tentativa; repetir CriarPedido devolve o pedido já gravado (ON CONFLICT DO NOTHING), sem duplicar. Cadastro de prato e mudança de etapa também podem ser repetidos.chave criada no Gateway
Circuit breakerUm circuito por serviço. Após 3 chamadas seguidas que falharam mesmo com retry, ele abre e recusa na hora (503 com Retry-After); depois de 15 s libera uma chamada de teste (meio-aberto) e fecha se ela passar. O Catálogo fora não abre o circuito de Usuários nem de Pedidos.DISJUNTOR_FALHAS=3, DISJUNTOR_ABERTO_SEGUNDOS=15
Fallback do cardápioA última lista boa de cada categoria fica em memória no Gateway e é servida, com "origem": "cache" e um aviso, quando o Catálogo não responde. O cache só exibe o cardápio: pedido é sempre conferido no banco.CACHE_CARDAPIO_SEGUNDOS=1800
Prazo propagadoO Pedidos chama o Catálogo com o tempo que resta da chamada do Gateway e, se o Catálogo falhar, avisa no metadado x-falha-dependencia: o Gateway não repete o CriarPedido (evita tempestade de retries) nem conta a falha contra o Pedidos.automático
Banco indisponívelO interceptador converte erro de conexão com o PostgreSQL em UNAVAILABLE, que o cliente pode repetir, e o pool testa cada conexão antes de usar, reabrindo sozinho quando o Cloud SQL volta.DB_POOL_MAX=3 por instância
Tempo realSe o stream gRPC AcompanharPedidos cair, o Gateway reabre com espera de 1 a 15 s e os navegadores veem "Reconectando..."; o LISTEN do PostgreSQL também reconecta e a tela segue consultando periodicamente.--timeout 3600 no Gateway e no Pedidos
PlataformaO Cloud Run substitui instâncias com falha e só manda tráfego a uma revisão nova depois que ela sobe; no SIGTERM o serviço marca o health check como NOT_SERVING e termina as chamadas em andamento.--min-instances 0, --max-instances 2, --cpu-boost

O que o usuário vê. Indisponibilidade nunca vira erro 500 genérico: UNAVAILABLE, DEADLINE_EXCEEDED, CANCELLED e RESOURCE_EXHAUSTED viram 503 com Retry-After e uma mensagem que o frontend apresenta em linguagem clara; o cardápio entra em modo de segurança com a lista salva; e a aba Saúde da cozinha mostra o health check de cada microsserviço e o estado de cada circuito.

Demonstração no Cloud Run. A falha é provocada pelo painel do GCP, sem mudar código: em Cloud Run › delivery-catalogo › Editar e implantar nova revisão › Variáveis e secrets, define-se FALHA_PERCENTUAL=100, e o interceptador passa a responder UNAVAILABLE como um serviço fora do ar. Ao vivo se observa o cardápio servido do cache, o pedido recusado com 503, o circuito aberto na aba Saúde e, no Cloud Logging, cada tentativa do retry (repetindo em ... ms) com o id da requisição. Com FALHA_PERCENTUAL=50 o retry absorve as falhas sem o usuário perceber; com FALHA_ATRASO_MS=12000 é o timeout que corta a espera. Voltando para 0, tudo se recupera em cerca de 15 s. Os 84 cenários de scripts/testar_gateway.py (status HTTP, autenticação e regras de negócio) passaram contra a URL pública do Gateway em 11/11/2026, e o roteiro da Tabela 5 também roda contra a nuvem (testar_resiliencia.py --url, com os comandos gcloud run services update de derrubar e religar).

Implantação. Tudo é implantado pelo Cloud Shell com um comando, bash scripts/gcp/cloud-run/implantar.sh, que pode ser repetido a cada versão: habilita as APIs, cria o repositório de imagens, liga o Cloud SQL, cria os segredos (senhas sorteadas; só a da cozinha é digitada) e as contas de serviço com papéis mínimos, constrói as imagens no Cloud Build, executa o job de migração e implanta os microsserviços e, por fim, Gateway e frontend, com o CORS apontando para a URL do frontend. Entre os testes, desligar.sh desliga o Cloud SQL, o maior custo, e para ou exclui as VMs do Trabalho 2; ligar.sh religa o banco antes da apresentação; o Cloud Run, com mínimo de zero instâncias, não cobra parado.
